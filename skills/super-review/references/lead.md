# Lead Workflow

Use the latest available version of each named model family unless the user or this skill explicitly specifies a version. Pass this rule to delegates.

The GPT-6-Sol (`gpt-6-sol`) lead at `max` effort owns the user's current objective, authorizations, phase transitions, resource state, and final handoff. Start one primary Sol child at `max` effort through T3 `delegate_task`. Assign that child to lead the phased review and use its own T3 delegates where the user or phase instructions call for them. Keep the active phase worker's thread ID for later phases, even if its model changes during recovery. If its first turn produces only a provider refusal, the fresh fallback child becomes the phase worker. Preserve explicit user choices, target permissions, and operating limits; leave unspecified access options at their T3 defaults.

In your own prompts, evidence, reviews, bundles, reports, and updates, use general review terms for the work and deliverables even when the request uses narrower labels; preserve the requested substance. Keep titles and summaries concrete: name the specific behavior or subject, distinguish observed from suspected, and state supported impact and limits. Pass this rule to the phase worker, and ask it to carry the rule into its delegates and later phases.

Read only the phase file needed next. Send its prompt verbatim after replacing run-specific placeholders. Give the child the current user request and limits in its initial assignment, followed by phase 1. After that phase finishes, send each next phase to the same child with T3 `t3_thread_send`:

1. [Phase 1](01-review.md) — broad review of the user-specified target.
2. [Phase 2](02-security-triage.md) — assess the first report's security claims and requested reproducible bundles.
3. [Phase 3](03-new-issues.md) — search for new security issues and reconcile relevant earlier reports.
4. [Phase 4](04-integrate-and-package.md) — integrate the security work into the main review and assemble the final report and requested bundles.

The deliverable remains the full review of the user's target. Security examination is one part of that review; fold its supported findings, negative results, and evidence limits into the main report. Fill only run-specific placeholders, including the target, output directory, and paths to prior phase outputs. Carry the user's original request and explicit revisions forward. Do not silently turn a phase result into proof that the broader objective is complete. For phases 2 and 3, use this skill's [security review guidance](security-review.md) and [triage criteria](triage.md). Give the child the applicable criteria and evidence.

Before advancing, inspect the child's returned work, actual artifacts, unfinished tasks, and resource state. Keep a compact record of phase status, evidence pointers, limitations, and outstanding user requests. Advance only when the phase is complete and its output is usable. If it cannot finish, preserve the partial result and give a limited handoff. For temporary changes, require a restorable baseline before work and verify cleanup afterward. Pass user revisions promptly to affected work and verify incompatible worker or tool activity has stopped. Call a bundle reproducible only when its contents support reproduction; otherwise label it an evidence bundle. Do not treat a finding count or a ZIP's existence as evidence of impact.

For a capacity error, continue the existing child thread with exactly `Continue where you left off.` when its phase brief reached the thread; if no thread was created, retry the original assignment. For a cybersecurity refusal during authorized work, if a new child's first turn produces only the provider refusal, with no assistant response or tool work, treat it as unstarted: start a fresh child with the identical full brief under the already-authorized GPT-6-Sol fallback at `max` effort, with Daybreak Blue when approved and exposed. Once a child has produced an assistant response or performed tool work, preserve its thread: switch its model to that fallback and send exactly `Continue where you left off.` when its current instructions are in place. Do not add a new confirmation or permission-research gate. Carry intervening revisions into the thread before resuming. The thread remains the phase worker for later phases. Apply this recovery rule to the worker's delegates too. Respect explicit target or provider access denials and provider retry limits; if continuation is unavailable, retain progress and report the limit.

After phase 4, verify that the main report covers the full requested review, including the security work and its limits. An unanswered applicable question or unperformed applicable requested test prevents full completion. Check the inventory of any archive and any restoration claims against the artifacts. Report what was completed, what remains uncertain, and where the deliverables are located. If another model invoked you as lead, return a compact status, supported high-level conclusions and limits, artifact paths, resource state, and outstanding work; leave detailed finding and reproduction material in the artifacts for direct authorized use.
